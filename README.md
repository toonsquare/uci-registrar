# UCI 등록 도우미

국립중앙도서관 **웹툰·웹소설 UCI 신청**을 도와주는 Windows 설치형 프로그램입니다.

로그인 → 대시보드 → 신청 폼 → 신청 → 심사 결과 조회 → 이력 관리까지의 흐름을 담고 있으며,
이력 CSV 내보내기를 함께 지원합니다.

작품은 포털 폼에 직접 입력해 신청합니다. **`작품 추가`로 카드를 늘리면 단건 신청을 작품마다 차례로 되풀이**합니다
(수행 계획서의 「복수 건 연속 신청 — 단건 폼 반복 호출」). 포털의 엑셀 일괄신청은 쓰지 않습니다 — 포털이 기능을 막아 두었고,
한 건씩 보내면 어느 작품이 왜 막혔는지도 바로 알 수 있기 때문입니다. 한 건이 막혀도 나머지는 계속 보내고, 접수된 카드는
지우고 막힌 카드만 사유와 함께 남깁니다.

---

## 먼저 알아야 할 것

### UCI는 신청 즉시 나오지 않습니다

포털에 신청하면 **접수번호**만 받고, 심사에 **업무일 3일**이 걸립니다.
결과는 이메일·카카오 알림톡으로 통지되며, 이 프로그램에서는 대시보드의
`심사 결과 조회` 버튼으로 확인합니다.

```
신청 → 접수번호 발급 → (업무일 3일 심사) → 발급완료 / 반려
       status: pending                      status: issued / rejected
```

### 발급 대상은 웹툰·웹소설뿐입니다

- 연재형 웹툰, 연재형 웹소설
- 위 콘텐츠를 단행본 전자출판물(epub, PDF 등)로 낸 자료

### 등록자번호가 먼저 필요합니다

UCI를 신청하려면 **등록자번호**를 미리 발급받아야 합니다. 요건은 다음과 같습니다.

> 웹콘텐츠(웹툰·웹소설) 제작 또는 유통에 참여하는 사업자이면서,
> 국내 관할 시·구청에서 **출판사신고**가 완료되어 **출판사 신고확인증**을 발급받은 출판사

```
시·구청 출판사신고 → 신고확인증 → seoji 계정 → 등록자번호 신청 → UCI 신청
```

등록자번호는 한 번 발급되면 **변경할 수 없습니다**. 정정은 `uci2025@korea.kr` 로 이메일 신청합니다.

**등록자번호는 계정에 묶여 있습니다.** 신청할 때 번호를 입력하는 게 아니라, 로그인하면 포털이 이미
알고 있습니다. 그래서 이 프로그램은 사용자가 적은 번호를 검사하지 않습니다 — 진짜인지 확인할
방법이 없으니까요.

대신 **로그인 직후 UCI 신청 화면이 열리는지 한 번 확인합니다.** 열리면 자격이 있는 것이고, 그 결과를
기억해 두었다가 다음부터는 확인하지 않습니다. (등록자번호는 바뀌지 않으므로 한 번이면 충분합니다.)
자격이 없으면 신청 버튼이 잠기고, 등록자번호를 새로 받은 뒤에는 설정 화면의 `지금 다시 확인` 을
누르면 앱을 껐다 켜지 않아도 됩니다.

설정 화면의 등록자번호 칸은 **참고용 메모**입니다. 포털에 보내지 않습니다.

> **저작권자 동의 필수** — 동의 없이 UCI를 등록하면 민·형사상 법적 책임이 등록자에게 있으며
> 발급이 취소될 수 있습니다. 신청 폼에 동의 확인 체크가 있습니다.

## 실제 포털 연동 상태

2026-08-03 실제 계정으로 포털 화면을 확인해 연동을 맞춰 두었습니다.
확인 내용은 폼 매핑 명세서에 정리돼 있습니다.

| 단계 | 상태 |
|---|---|
| 로그인 | 선택자 확보 · 성공 판정 기준(`a[href*=logout.do]`)까지 확인 |
| 신청 폼 | **필수 항목 15개 전부 매핑 완료** |
| 현황 조회 | 작품명 검색 · 결과표 열 위치 확인 |
| 실제 신청 실행 | **아직 해본 적 없음** — 진짜 접수가 되므로 확인 후 진행 |

### 신청 폼에 필수 항목만 담은 이유

포털 신청 화면에는 입력칸이 46개 있지만, 실제로 검사하는 것은 그중 일부입니다.
포털의 검증 코드(`fn_save()`)를 그대로 읽어서 **정말 필요한 항목만** 폼에 넣었습니다.

| 어디서 입력 | 항목 |
|---|---|
| **설정** (한 번만) | 담당자명 · 이메일 · 휴대폰 · 결과 안내방법 · 개인정보 수집 동의 |
| **작품마다** | 유형 · 연재유형 · 작품명 · 작가역할 · 작가명 · 연령등급 · 장르 · 연재처 · 연재상태 · 가격 · 회차 범위 · 저작권자 동의 |

담당자 정보는 작품마다 바뀌지 않으므로 설정에 저장해 두고 신청할 때 자동으로 채웁니다.
제작사와 등록자번호는 **로그인하면 포털이 이미 알고 있어** 프로그램이 건드리지 않습니다.

### 여러 작품을 한 번에 신청하려면

신청 화면에서 **작품 하나가 카드 하나**입니다. 맨 아래 `작품 추가`를 누르면 카드가 늘어납니다.
모든 카드를 먼저 검사한 뒤(하나라도 틀리면 아무것도 보내지 않음) 카드마다 단건 신청을 차례로 보냅니다.

```
카드 1장  →  단건 신청 (포털 폼에 직접 입력)
카드 2장~ →  단건 신청을 작품마다 차례로 (건당 5~30초, 진행은 신청 단추에 n/N 로 표시)
```

같은 작품명이 포털에 있으면 그 작품에서 멈춰 단건과 똑같이 「회차 추가 / 새 작품으로 등록 / 취소」를 묻고, 고르면 이어 갑니다.
담당자 정보와 저작권자 동의는 화면에서 한 번만 받습니다. 웹툰과 웹소설을 섞어도 됩니다 — 한 건씩 보내므로 양식 제한이 없습니다.

엑셀 일괄신청 자동화(`applyBulk`, `bulk-excel.js`, 공식 양식)는 본체에 남아 있지만 화면에서는 부르지 않습니다.

### 작가는 한 줄에 한 사람, 이력은 로그인 직후 포털에서 전부 읽어 저장합니다

포털 신청 폼은 작가를 「역할 + 이름」 줄로 받고 「+」(fn_addAuthor)로 줄을 늘립니다. 서버에는 줄 목록이
넘어가므로 글 작가와 그림 작가가 다르면 두 줄이어야 합니다 (2026-10-16 확인). 화면도 같은 구조이고
(`authors: [{ role, name }]`), 포털 채우기는 둘째 줄부터 포털의 + 함수를 부른 뒤 n번째 칸에 넣습니다.
일괄 양식은 "글,그림 / 홍길동,김작가" 처럼 쉼표 병렬 표기로 받습니다. 예전 기록의 writerRole/writer 한 쌍은
한 줄로 읽습니다 (`authorsOf`).

로그인이 끝나면 바로 대시보드로 가고, 그 뒤에서 포털의 「UCI 신청 현황」 전체(10건씩 쪽 넘김)와 각 건의 상세,
발급 건의 회차 범위를 읽어 본체 메모리에 둡니다 (`auth:login` → `startSync` → `syncPortal`). 파일에는 쓰지 않습니다. 읽기는 신청·조회가
쓰는 숨은 창과 다른, 불러오기 전용 숨은 창(`portal.background`, 같은 세션 파티션)에서 돌아 신청·조회와 겹쳐도 서로
기다리지 않습니다. 각 화면은 들어갈 때 본체의 이력을 받아 그리고(지연 로딩), 뒤에서 한 쪽을 읽을 때마다
`records:syncProgress` 로 알려 와 보고 있는 화면을 다시 그립니다. 진행·실패(다시 시도)는 상단 바에 작게 보입니다.
대시보드 숫자·신청 이력(쪽 나눔·검색·상태 필터)·이전 신청 불러오기·CSV 는 모두 메모리의 것만 써서
포털을 기다리지 않고 빈 값도 없습니다. 로그인은 매번 건수만큼 걸리고(상세 한 건에 포털 왕복 한 번, 3건씩 동시),
켜져 있는 동안의 「새로고침」은 상세를 안 읽은 새 줄만 읽습니다. 이력의 「새로고침」은 전체를 다시 읽고, 신청 직후에는 새 줄이 나오는
쪽까지만 다시 읽습니다 (`scope: 'recent'`). 전체 읽기 때 포털에 없던 기록은 `goneAt` 을 달아 화면에서 뺍니다 —
화면에는 포털에 있는 것만 보입니다.

줄마다 포털의 신청 키(`fn_goEdit('<recKey>')`)를 뽑아 이 PC 의 이력과 짝을 맞춥니다 (`store.mergePortalRecords`).
같은 작품명을 두 번 낸 줄도 키가 다르므로 합쳐지지 않습니다. 포털 목록에는 작품명·상태·UCI·날짜뿐이라
작가·장르·연재처·가격·연령등급·반려 사유는 상세 화면(`S90300000000.do?schM=view&type=info` 에 recKey 를 POST)에서
읽습니다 — 현황 화면을 한 번 연 뒤 그 안에서 fetch 로 HTML 을 받아 DOMParser 로 읽으므로 창을 옮기지 않습니다
(`getApplicationDetails` → `store.applyDetail`). 회차 시작·끝은 상세 화면에 없어 조회/정정의 「콘텐츠목록 다운로드」
엑셀(키 목록을 한 번에 POST)에서 읽습니다 (`getIssuedEpisodes` → `store.applyEpisodes`). 포털 자동화는 숨은 창
하나를 쓰므로 창을 쓰는 동작은 들어온 차례대로 하나씩 돌립니다 (`inTurn`).

### 같은 작품명이 이미 있으면 포털이 묻습니다

포털은 접수 전에 같은 작품명이 등록돼 있는지 확인하고, 있으면 접수하지 않고 중복 확인 창을 엽니다
(2026-10-15 포털 코드에서 확인). 창에는 「선택회차추가」와 「신규작품등록」 두 갈래가 있습니다.
프로그램은 그 창을 열지 않고 요청만 가로채서 같은 두 갈래를 화면에 보여 줍니다. 사용자가 「새 작품으로
등록하고 계속」을 고르면 포털의 신규작품등록 버튼과 같은 동작(새 작품 표식을 세우고 같은 폼을 접수 주소로
전송, 일괄은 업로드 재호출)을 합니다. 고르기 전에는 아무것도 보내지 않고 이력에도 남기지 않습니다.
회차 추가 자체는 프로그램이 다루지 않으며 포털 화면을 열어 줍니다.

비슷한 작품을 연달아 신청할 때는 작품 카드의 「이전 신청 불러오기」로 이력의 입력값을 가져와 고쳐 씁니다.
회차 범위는 비워 둡니다.

### 처음 켜면 교육이 뜹니다

처음 실행하면 로그인 화면 위에 **대화형 교육**이 뜹니다. 선배 캐릭터와 대화하며 UCI가 무엇인지,
누가 받을 수 있는지, 신청 순서와 저작권자 동의까지 배우고, 중간중간 퀴즈로 확인합니다. (약 15분)

```
1~4장  대화 + 퀴즈 (UCI란 · 왜 UCI로 · 등록자번호 · 신청 순서)
5장    연습 — 프로그램 실제 화면에서 담당자 정보 → 신청 → 10초 뒤 결과 조회 → UCI 확인
```

연습은 **연습 모드**로 돕니다. 포털에는 아무것도 보내지 않고, 끝나면 연습 기록은 지워지고
실제 로그인 화면으로 돌아옵니다. 연습 중 입력한 담당자 정보는 그대로 남아 실제 신청에 쓰입니다.

건너뛰어도 되고, `도움말` 메뉴에서 언제든 교육·연습을 다시 할 수 있습니다.

교육 페이지는 [`src/renderer/edu/`](src/renderer/edu/) 에 있습니다. 인물·배경 일러스트는 `edu/img/` 에 있습니다.

### 연재처는 목록에서 고릅니다

포털의 연재처 입력칸은 직접 타이핑할 수 없고 팝업에서 골라야 합니다.
팝업의 목록(12곳)과 코드를 미리 확보해 드롭다운으로 만들어 두었습니다.

```
네이버 웹툰 · 네이버 웹소설 · 네이버 시리즈 · 카카오웹툰 · 카카오페이지 · 리디
노벨피아 · 레진코믹스 · 조아라 · 탑툰 · 봄툰 · 문피아
```

> 자사 플랫폼처럼 이 목록에 없는 곳은 선택할 수 없습니다. 그런 작품이 있으면 알려주세요.

### 연동 모듈 인터페이스와 API 자리

화면과 IPC 계층은 [`src/main/providers/interface.js`](src/main/providers/interface.js) 에 정의된 동작
아홉 가지(login · logout · getSession · verifyAccess · apply · applyBulk · checkStatus · listApplications · lookup)만
보고 동작합니다. 구현은 셋이고 설정 `mode` 로 고릅니다.

| mode | 파일 | 내용 |
|---|---|---|
| `portal` (기본) | `providers/portal.js` | 국립중앙도서관 포털 화면 자동입력 — 내장 브라우저로 포털 폼을 채워 포털의 신청 버튼을 누름 |
| `mock` | `providers/mock.js` | 연습·데모용 모의 연동 |
| `api` | `providers/api.js` + `api.json` | **국립중앙도서관 API 연동 자리.** 규격이 제공되지 않아 비어 있고, 모든 동작이 "미개통" 으로 답함 |

API 가 개통되면 `api.json` 에 주소·인증·경로를 적고 `api.js` 의 각 동작을 규격에 맞춰 채운 뒤 설정을 `api` 로
바꾸면 됩니다. 화면·이력·시험은 손댈 것이 없습니다. 규격을 모르는 채로 가정 호출 코드를 넣어 두지는
않았습니다 — 나중에 맞춰 고치는 일이 더 커지기 때문입니다. 세 구현이 인터페이스를 다 갖췄는지는 불러올 때와
시험에서 확인합니다.

### 두 가지 모드

| 모드 | 하는 일 |
|---|---|
| **모의 연동** | 프로그램 안에서 접수·심사·발급을 흉내낸다. 포털에 접속하지 않는다 |
| **실제 포털 연동** | 숨은 브라우저로 포털을 열어 사람이 하듯 로그인·입력·신청한다 |

모의 연동은 심사 대기를 **10초**로 줄여 두어 흐름을 바로 확인할 수 있습니다.
작품 URL에 `reject` 가 들어 있으면 반려 결과가 나옵니다.

`selectors.json` 의 `configured` 를 `false` 로 바꾸면 **포털 접속을 전면 차단**합니다.
문제가 생겼을 때 되돌리는 스위치입니다.

### 시험 실행

```bash
npm run test:all
```

시험은 실제 포털에 접속하지 않습니다. 포털 제공자를 건드리는 구간은
`configured` 를 내려 차단 여부만 확인합니다.

`npm run test:demo` 는 데모 빌드를 실제로 띄워 **로그인 → 대시보드 → UCI 신청 →
폼 입력 → 신청하기 → 이력** 까지 눌러 봅니다.

신청 제공자는 두 개 모두 같은 함수 모양을 가집니다.

```js
login({ loginId, password })  // -> { ok, user?, error? }
logout()                      // -> { ok }
getSession()                  // -> user | null
verifyAccess()                // -> { ok, error? }  UCI 신청 자격(등록자번호) 확인
apply(meta)                   // -> { ok, appliedAt?, status:'pending', error? }
applyBulk(items)              // -> { ok, appliedAt?, status:'pending', count?, error? }  엑셀 일괄
checkStatus(record)           // -> { ok, status, uci?, reason?, error? }
lookup(uci)                   // -> { ok, record?, error? }
```

덕분에 화면 코드는 지금이 모의인지 실물인지 알 필요가 없습니다.

### 신청 이력의 상태값

| status | 뜻 | 포털의 신청상태 |
|---|---|---|
| `pending` | 접수됨, 심사중 | 접수 · 재접수 · 회차추가 |
| `needsFix` | 보완요청 — 담당자가 포털에서 고쳐야 함 | 보완요청 |
| `issued` | 발급완료 (UCI 있음) | 완료 |
| `rejected` | 반려 | 처리불가 · 삭제 |
| `failed` | 신청 자체가 실패 (접수되지 않음) | (해당 없음) |

## 실제 포털에 연동하는 방법

대상은 국립중앙도서관 **ISBN·ISSN·UCI·납본 시스템** (<https://www.nl.go.kr/seoji/>) 입니다.

### 사전 조사 결과 (2026-07-30, 계정 없이 공개 페이지에서 확인)

자동화를 막는 흔한 장애물이 **셋 다 없습니다.**

| 항목 | 결과 |
|---|---|
| 보안키보드 (nProtect·AhnLab 등) | 없음 — 비밀번호 칸에 값을 넣을 수 있음 |
| CAPTCHA | 없음 |
| 로그인 폼이 iframe 안에 있음 | 아님 — 최상위 문서에 있음 |

로그인 화면 구조도 확인해서 `selectors.json` 에 **이미 채워 두었습니다.**
계정 종류는 세 가지이고, 기본 선택된 `출판사·기관` 기준으로 넣어 두었습니다.

| 계정 종류 | 아이디 | 비밀번호 | 로그인 버튼 |
|---|---|---|---|
| 출판사·기관 (기본) | `#publishID` | `#publishPW` | `#publishBtn` |
| 공공간행물 디지털납본 | `#digitalID` | `#digitalPW` | `#digitalBtn` |
| 학위논문 디지털납본 | `#thesisID` | `#thesisPW` | `#thesisBtn` |

세션 유지 시간은 1시간입니다.

### 설정 파일은 어디에 있나

프로그램 **설정** 화면의 `파일 열기` 버튼으로 바로 열 수 있습니다. 실제 경로는 아래와 같습니다.

```
%APPDATA%\UCI 등록 도우미\selectors.json
```

설치 파일 안의 원본은 읽기 전용이라, 첫 실행 때 이 위치로 한 벌 복사됩니다.
**메모장으로 고치고 저장하면 즉시 반영됩니다** — 프로그램을 다시 설치하거나 껐다 켤 필요 없습니다.
잘못 고쳐서 꼬였으면 설정 화면의 `기본값 복원`을 쓰면 됩니다. (JSON 문법이 깨지면 사유가 화면에 뜹니다.)

개발 중에는 `npm start` 로 띄운 앱도 같은 파일을 씁니다.
`src/main/providers/selectors.json` 은 새 사본을 만들 때 쓰는 원본입니다.

### 포털 화면이 바뀌었을 때

연동은 이미 맞춰져 있습니다. 포털이 개편돼서 동작이 깨지면 아래 순서로 다시 맞춥니다.

1. 크롬으로 포털에 로그인 → `UCI` → `UCI 신청` → `작품 건별 신청`.
2. `F12`(개발자도구) → `Console` 탭.
   (크롬이 `allow pasting` 을 입력하라고 하면 그대로 치고 Enter)
3. [`scripts/dump-form.js`](scripts/dump-form.js) 내용을 통째로 붙여넣고 Enter.
   화면의 입력칸·버튼과 선택자가 **클립보드에 복사됩니다.**
4. `UCI 신청 현황 조회` 화면에서도 한 번 더 실행합니다.
5. 두 결과를 보고 설정 화면의 `파일 열기` → `selectors.json` 의 값을 교체합니다.

> 비밀번호 칸은 위치만 기록하고 값은 읽지 않습니다.
> 실제 화면에서 검증했을 때 입력칸 전부 선택자가 정확하고 유일했습니다.

문제가 생겼는데 원인을 모르겠으면 `configured` 를 `false` 로 바꿔 두세요.
포털 접속을 전면 차단해서, 잘못된 설정으로 엉뚱한 요청이 나가는 것을 막습니다.

`configured` 가 `false` 인 동안에는 포털에 접속조차 하지 않습니다.
설정이 덜 된 상태로 접속을 시도하다 응답 대기로 멈추는 것을 막기 위한 장치입니다.

문제가 생기면 설정에서 **포털 연동 중 브라우저 창 표시**를 켜세요.
자동화가 실제로 무엇을 하고 있는지 눈으로 볼 수 있습니다.

> 이 포털은 오류를 `alert()` 창으로 알립니다. 숨은 창에서 알림창이 뜨면 자동화가 멈춰버리므로,
> [`portal-preload.js`](src/main/providers/portal-preload.js) 가 알림창을 가로채 메시지만 받아
> 그대로 실패 사유로 보여줍니다.

> 포털 세션은 1시간입니다. 여러 작품을 이어서 신청하거나 한참 뒤에 결과를 조회하면 그 사이에
> 세션이 끊길 수 있습니다. **로그인 정보 저장**을 켜 두면 세션이 끊겼을 때 조용히 다시 로그인하고
> 이어서 진행합니다. 저장해 두지 않았으면 `포털 세션이 만료되었습니다` 라고 알려줍니다.

> 포털이 개편되면 화면 구조가 바뀝니다. 그때도 고치는 곳은 `selectors.json` 한 파일입니다.

## 저장되는 데이터

Windows 기준 `%APPDATA%\UCI 등록 도우미\` 폴더에 두 파일이 생깁니다.
설정 화면의 `폴더에서 보기`로 바로 열 수 있습니다.

| 파일 | 내용 |
|---|---|
| `uci-data.json` | 프로그램 설정 · 저장된 로그인 정보 (프로그램이 관리). 신청 이력은 여기 쓰지 않는다 — 로그인마다 포털에서 새로 읽어 메모리에만 둔다 |
| `uci-data.json.bak` | 직전 저장본 — 자동 복구에 쓰임 |
| `selectors.json` | 포털 연동 설정 (담당자가 직접 고치는 파일) |

### 설정이 사라지지 않도록 하는 장치

담당자 정보·저장된 로그인이 깨지면 다시 입력해야 하므로 아래 장치를 두었습니다. (신청 이력은 포털이 원본이라
파일에 두지 않는다 — 2026-10-22. 그 전에는 이력도 이 파일에 있었다.)

- **원자적 저장** — 임시 파일에 다 쓴 뒤 이름을 바꿔치기합니다. 저장 도중 앱이 죽어도
  반쪽짜리 파일이 남지 않습니다.
- **직전 저장본 보관** — 매 저장마다 `.bak` 을 남깁니다. 파일이 깨지면 여기서 되살립니다.
- **손상 시 덮어쓰기 금지** — 되살릴 백업조차 없으면 그 실행에서는 **저장을 아예 막습니다.**
  빈 상태가 원본을 덮어써 복구 가능성이 사라지는 것을 막기 위해서입니다. 이때는 화면 위에
  빨간 경고가 뜨고, 손상된 원본은 `uci-data.corrupt-<시각>.json` 으로 보관됩니다.
- **중복 실행 차단** — 창을 두 개 띄우면 각자 설정을 통째로 덮어써 서로의 것을 지웁니다.
  두 번째 실행은 조용히 종료되고 기존 창이 앞으로 나옵니다.

로그인 정보를 저장하도록 선택하면 비밀번호는 운영체제 보안 저장소(Windows DPAPI)로
암호화되어 보관됩니다. JSON 파일에 평문으로 남지 않습니다.
